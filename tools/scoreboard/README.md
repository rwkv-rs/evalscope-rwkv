# Scoreboard publication

The uploaders target the current [`scoreboard-v1` contract](https://github.com/rwkv-rs/scoreboard-rwkv#field-与作答元数据).
Scoreboard owns its database and frontend; EvalScope only publishes over HTTP.
No model comparison pairs or display multipliers are generated by the uploaders.

## Publish each completed benchmark

The native callback in `evalscope/utils/scoreboard.py` reads the completed benchmark's
saved report, predictions and reviews. It preserves the reported scores, decoding
parameters, prompt, raw output, extracted answer and generation details.

Create a metadata JSON file using your actual weight identity and benchmark fields:

```json
{
  "weight_sha256": "<actual 64-character lowercase weight SHA-256>",
  "weight_display_name": "RWKV7-g1i-1.5B",
  "wkv_mode": "fp32io16",
  "benchmark_fields": {"gsm8k": "math", "general_fc": "tool-use"}
}
```

Each selected benchmark needs exactly one field. Choose a stable lowercase slug
matching `^[a-z][a-z0-9_-]{0,63}$`; fields are not inferred from benchmark names or
model generations. Optional `languages` and `tags` remain independent metadata.
Old metadata files must replace `comparison` with `benchmark_fields`.
Use a display label rather than a filename (for example, `RWKV7-g1i-1.5B`,
without `.pth`). The current upstream comparison dashboard recognizes G1i/G1j
labels; other generations such as G1h remain available in evaluation history.
The uploader does not rename a model to force it into a comparison group.

```bash
export SCOREBOARD_API_BASE_URL=http://127.0.0.1:8000
export SCOREBOARD_PUBLICATION_TOKEN=<publication-token>
bash scripts/eval_with_scoreboard.sh metadata.json --model <model> --datasets gsm8k
```

For already completed artifacts, call `publish_benchmark_callback(work_dir,
model_id, benchmark, metadata_path)` directly; no evaluation rerun is required.

## Migrate the legacy database once

The migration tool reads completed, non-temporary EvalScope tasks from the legacy
database in a read-only snapshot through `psql`. It does not connect to the new
Scoreboard database. Provide the existing model-name-to-weight mapping as
`models.json`, and a separate `fields.json` such as `{"bfcl_v4": "tool-use"}`.
The legacy database does not store a primary field, so every benchmark must be
explicitly mapped before uploading.

```json
{
  "<legacy model_name>": {
    "weight_sha256": "<actual 64-character lowercase weight SHA-256>",
    "weight_display_name": "<weight display name>",
    "wkv_mode": "fp32io16"
  }
}
```

```bash
export LEGACY_SCOREBOARD_DSN=<read-only-legacy-database-connection>
python -m tools.scoreboard.migrate_legacy --model-map models.json --benchmark-fields fields.json --dry-run
python -m tools.scoreboard.migrate_legacy --model-map models.json --benchmark-fields fields.json
```

Both paths create/reuse a campaign, PUT each task atomically, then finalize. A
repeated upload uses deterministic idempotency keys; complete campaigns are not
uploaded again. HTTP failures propagate, leaving native artifacts or the legacy
database unchanged for a retry. Neither path writes additional evidence files.

Evidence is capped at 20 samples per outcome (`correct`, `incorrect`, `unanswered`,
and native `undetermined`). Scores remain the full report scores;
`diagnostics.samples_total` and `diagnostics.truncation_rate` count all source
samples, including those omitted from uploaded evidence. The frontend's sample
list therefore contains representative evidence, not every evaluation record.
Each request is checked against the current server limits of 128 MiB gzip /
512 MiB raw, introduced by [Scoreboard PR #6](https://github.com/rwkv-rs/scoreboard-rwkv/pull/6).
